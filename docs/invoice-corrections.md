# 청구 이력 정정 — 2026-10-23

예약 상세에서 인보이스를 열고 상단의 **청구 이력 정정**을 펼친다. 해당 행의 **금액 정정** → 정수 원 단위 금액 입력 → **저장** 순으로 사용한다. 테스트 청구는 0원으로 정정할 수 있다. 행은 남고 이전 청구액 합계에서 해당 금액만 제외된다.

정정은 `reservation_invoices.amount`를 해당 예약·청구 건에 한정해 변경한다. 합계는 저장 후와 다음 인보이스를 열 때 서버에서 다시 읽는다. 이전 금액이 이미 변경된 경우 409로 응답하여 다른 직원의 정정을 덮어쓰지 않는다. 두 관리자 계정 모두 기존 서버 권한 정책을 사용한다. DB 스키마 변경은 없다.

인쇄 전에는 청구 이력 최신 합계를 다시 확인한다. 변경이 발견되면 최신 금액을 표시하고 재확인을 요청한다. 이번 청구 저장 후에는 인쇄가 끝날 때까지 이전 청구액에 이번 금액을 더하지 않는다. 인쇄 종료 후에는 이번 입력을 비우고 이력을 다시 읽는다. 저장/인쇄 도중 중복 클릭 및 금액 변경을 막는다. 이력 조회에 실패하면 0원으로 취급하지 않고 인쇄를 중단한다.

기존과 같이 인쇄창을 열기 전에 청구 이력이 저장된다. 브라우저에서는 실제 인쇄 완료와 사용자의 취소를 확실하게 구분할 수 없다. 잘못 저장된 청구는 이력에서 정정한다. 이미 내려받은 인보이스 파일 자체는 바뀌지 않는다.

검증: `npm run test:invoices`(6개)로 정정 후 합계, 0원 처리, 예약 범위 제한, 동시 수정 충돌, 인증 차단, 입력값 및 전체 이력 조회를 확인한다. 기존 보안 테스트도 실행한다. 운영 DB는 컬럼 존재 여부만 확인했으며 청구 데이터를 변경하지 않았다.

가상 데이터로 실제 InvoiceModal/InvoiceHistoryEditor를 브라우저에서 실행했다(저장·인쇄 어댑터만 모의 처리). 초기 50만 원 이력 중 30만 원을 0원으로 정정 → 이전 청구액 20만 원. 이번 10만 원 청구의 인쇄 스냅샷에는 이전 20만 원/이번 10만 원/잔금 70만 원(총액 100만 원)을 확인했다. 다시 열면 이전 청구액 30만 원으로 반영되며 저장은 1건이었다.

2026-10-23 사용자가 Git 업로드를 승인했다. main 브랜치로 커밋/푸시하며, 호스팅 서비스의 배포 완료 여부는 별도로 확인한다. 실제 운영 청구 이력 정정은 사용자가 대상 건을 확인한 뒤 진행한다.
