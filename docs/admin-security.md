# 관리자 인증 보강 체크포인트 — 2026-10-22

## 완료한 변경

- 브라우저와 서버가 공식 `@supabase/ssr` 쿠키 세션을 공유한다. 기존 localStorage 세션에서 자동 이전하지 않으며 적용 후 한 번 다시 로그인한다.
- 관리자 페이지는 서버에서 `auth.getUser()`로 사용자 검증 후 관리자 정책을 적용한다. `admin_user`, `admin_email` 쿠키는 인증·권한 근거로 사용하지 않는다.
- 직원 `cjjbni@cjjbni.com`, 대표 `ronaldo1109@naver.com`은 확인된 이메일에 같은 정책을 적용한다. 일반 사용자 및 anonymous 사용자는 관리자 접근을 허용하지 않는다.
- 추가 관리자는 서버 환경변수 `ADMIN_EMAILS`(쉼표 구분) 또는 서버에서만 설정 가능한 `app_metadata.role=admin`으로 등록한다. 사용자가 수정할 수 있는 `user_metadata`는 무시한다.
- `/api/dispatch`는 예약 조회 및 엑셀 생성 전에 서버 인증을 검사한다. 보호되는 응답에는 `private, no-store`를 사용한다.
- 문서 업로드/삭제, 예약 이동, 구글 좌석표 동기화도 같은 관리자 정책을 사용한다. 기존 Bearer 토큰 호출과 쿠키 세션 호출을 모두 지원하며 잘못된 Bearer 헤더는 쿠키로 대체 통과시키지 않는다.
- 인보이스 예약확인서는 공개 다운로드 API가 아니라 브라우저 인쇄 방식이다. 청구 이력 저장 전 및 인쇄 직전 서버 세션을 재확인한다. HWPX 다운로드도 생성 전에 서버 세션을 재확인한다.
- 로그아웃은 Supabase 세션을 종료하고 브라우저 상태를 비운 뒤 로그인 화면을 새로 연다.

## 검증

`npm run test:security`: 운영 계정/예약/비밀번호를 사용하지 않는 가상 데이터 기반 검증. 두 관리자 허용, 일반 계정 및 사용자 메타데이터 위조 거부, 만료 토큰 거부, 위조 쿠키 접근 차단, 세션 갱신 쿠키 전달, 비인증 엑셀 생성 전 차단, 두 관리자 엑셀 생성 및 파일 내용, 인보이스/HWPX용 세션 재검사, 관련 API 인증, 로그아웃, 좌석 동기화 차단을 확인한다.

`npm run test:confirmation`: 기존 확정서 날짜/집계/상품 매칭 검증.

추가로 로컬 HTTP에서 위조 `admin_user` 쿠키만 보낸 관리자 화면의 로그인 리디렉션 및 다운로드/관련 API의 401을 확인한다.

## 범위와 남은 점검

이 변경은 관리자 진입 및 서버 API의 인증과 권한을 보강한다. 브라우저의 Supabase 직접 조회와 저장은 기존 RLS/Storage 정책의 적용을 받는다. 운영 DB의 RLS, 공개 파일 URL, 버킷 정책을 조회하거나 수정하지 않았으므로 전체 데이터 접근이 안전하다고 단정하지 않는다. 이미 브라우저에 표시되거나 내려받은 개인정보를 세션 종료로 회수할 수는 없다.

원본 예약 데이터, 상품 일정, DB 구조, cron 인증 및 일반 고객 예약 흐름은 변경하지 않았다. 환경변수 값·토큰·실예약 개인정보를 테스트 기록에 남기지 않는다.
